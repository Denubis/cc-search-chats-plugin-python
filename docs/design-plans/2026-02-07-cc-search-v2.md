# CC Search Chats v2 Design

## Summary

This design describes a rewrite of the cc-search-chats Claude Code plugin from a bash/embedded-Python script into a standalone Python package. The tool enables context recovery and cross-referencing of Claude Code chat history — particularly useful when sessions exceed token limits and Claude Code compresses them, discarding earlier context.

The new implementation uses SQLite with FTS5 for fast keyword search across conversations, session discovery heuristics to auto-identify recent substantial chats (useful for crash recovery), and first-class compression awareness through an "epoch" model that segments conversations before and after each compression event. The package is dependency-free (stdlib only) and runnable via `uvx cc-search-chats`, with all commands supporting both human-readable and JSON output for subagent consumption. The architecture follows Functional Core / Imperative Shell: pure functions for parsing JSONL records and building queries, isolated from file I/O and database operations.

## Definition of Done

Rewrite the cc-search-chats Claude Code plugin from bash/embedded-Python to a proper Python package. The tool provides context recovery and cross-referencing of Claude Code chat history — recovering from compression failures, searching sessions, and extracting conversations.

**Primary deliverables:**
1. Python package runnable via `uvx cc-search-chats` — zero external dependencies (stdlib only)
2. SQLite FTS5 index with JIT indexing (index on first search, not eagerly)
3. Core commands: `search`, `index`, `list`, `extract`, `context`
4. Session discovery heuristic: find most recent substantial conversations by mtime + file size
5. Claude Code plugin wrapper — command definition in `commands/*.md`, skill in `skills/*/SKILL.md`
6. `--json` output mode on all commands for subagent consumption
7. Existing bash script replaced entirely

**Success criteria:**
- Can search an 8MB+ chat session without hanging
- Can recover context from a crashed/compressed session by running `uvx cc-search-chats extract` with no arguments (auto-discovers recent substantial session)
- Sonnet subagent can invoke via Bash tool and get structured JSON back
- Tests exist for JSONL parsing, indexing, search, and session discovery

**Out of scope:**
- AI-powered summarisation (no LLM API calls)
- Web UI
- Semantic/vector search
- Modifying or deleting chat history

## Glossary

- **JSONL**: JSON Lines format — one JSON object per line, newline-delimited
- **FTS5**: SQLite's Full-Text Search extension (version 5) for efficient keyword search
- **Compression**: Claude Code's mechanism for reducing token usage by summarising earlier conversation context when sessions grow large. Appends a `compact_boundary` record followed by a summary message.
- **Epoch**: A segment of a conversation delimited by compression events. Epoch 0 is pre-compression, epoch 1 is after the first compression, etc.
- **compact_boundary**: A JSONL record type (`type=system`, `subtype=compact_boundary`) marking where compression occurred
- **JIT indexing**: Just-In-Time indexing — the index is updated only when a session file's mtime indicates changes, not eagerly
- **Functional Core / Imperative Shell (FCIS)**: Architecture pattern separating pure functions (no I/O, deterministic) from imperative code (file/DB operations)
- **uvx**: uv's tool runner for executing Python packages without explicit installation
- **WAL mode**: Write-Ahead Logging, SQLite's journaling mode enabling concurrent reads during writes
- **Materialised view**: A database view whose results are cached and updated via triggers (manually implemented in SQLite)
- **Subagent**: A Claude instance (typically Sonnet) invoked via the Task tool to perform a delegated task
- **Sidechain**: In Claude Code's message tree structure, a branch off the main conversation path (e.g., from a retry or alternative response)
- **BLNS**: Big List of Naughty Strings — a collection of strings known to cause problems with string handling (null bytes, unicode edge cases, escape sequences, SQL injection attempts)
- **t-strings**: Python 3.14 template strings (PEP 750) for safe string interpolation that prevents injection of untrusted content

## Architecture

Python package with Functional Core / Imperative Shell separation. The core contains pure functions for parsing JSONL records and building search queries. The shell handles file I/O, SQLite operations, and CLI interaction.

### Package Structure

```
src/cc_search_chats/
    __init__.py
    cli.py                  # argparse entry point (imperative shell)
    core/
        __init__.py
        models.py           # dataclasses: SessionRecord, Session, CompactEvent
        parser.py           # JSONL line → SessionRecord (pure)
        search.py           # FTS5 query construction (pure)
        discovery.py        # Session ranking by mtime + size (pure, takes metadata as input)
    storage/
        __init__.py
        index.py            # SQLite: create DB, index sessions, execute queries
        schema.sql          # DDL for tables, FTS5, triggers, materialised views
```

### Data Model

Claude Code stores sessions as JSONL files at `~/.claude/projects/<encoded-path>/<session-uuid>.jsonl`. The encoded path replaces `/` with `-` in the project's absolute path. Each line is a JSON object with a `type` field.

**Record types relevant to this tool:**

| type | Subtype | Purpose |
|------|---------|---------|
| `user` | — | User message. `message.content` is a string. |
| `assistant` | — | Assistant message. `message.content` is a list of `{type: "text"/"tool_use", ...}` objects. |
| `summary` | — | Session-level summary. Contains `summary` (text) and `leafUuid`. |
| `system` | `compact_boundary` | Compression event. Contains `compactMetadata.trigger`, `compactMetadata.preTokens`. |

Other types (`progress`, `queue-operation`, `file-history-snapshot`) are ignored during indexing.

**Compression model:** A session's JSONL file is append-only. Compression does not create new files. Instead, a `compact_boundary` record is inserted, followed by a user message containing the compression summary ("This session is being continued from a previous conversation..."). Messages before the boundary are the "lost context." The `epoch` concept segments the conversation: epoch 0 is pre-compression, epoch 1 is after the first compression, etc.

**Tree structure:** Messages link via `uuid` and `parentUuid`. After a compact_boundary, the boundary record has no parent (it's a new tree root). The post-compression user message parents to the boundary.

**Resilience:** The epoch model is additive — if `compact_boundary` records are absent or their format changes, all messages default to epoch 0 and the tool works as a flat search/extract tool. Unknown record types and unrecognised fields are silently skipped. The tool must never crash on format changes; it degrades gracefully to epoch-unaware operation.

### Database Schema

SQLite database at `~/.cc-search-chats/index.db`. WAL mode for concurrent read safety.

**`session` table:**
- `session_id` TEXT PK
- `project_path` TEXT — original project directory path
- `file_path` TEXT — absolute path to the JSONL file
- `file_size` INTEGER
- `modified_at` TEXT — file mtime at last index
- `indexed_at` TEXT
- `summary` TEXT — from most recent `type=summary` record

**`compact_event` table:**
- `uuid` TEXT PK — the compact_boundary record's uuid
- `session_id` TEXT FK → session
- `epoch` INTEGER — this event starts this epoch number (first compression = 1)
- `timestamp` TEXT
- `trigger` TEXT — "auto" or "manual"
- `pre_tokens` INTEGER
- `summary_text` TEXT — extracted from the user message following the boundary

**`message` table:**
- `uuid` TEXT PK
- `session_id` TEXT FK → session
- `parent_uuid` TEXT
- `epoch` INTEGER — 0 = pre-compression, increments per compact_boundary
- `timestamp` TEXT
- `role` TEXT — "user" or "assistant"
- `text_content` TEXT — plaintext extracted from message content
- `is_sidechain` BOOLEAN

**`message_fts` FTS5 virtual table** on `text_content`, with triggers on `message` to keep in sync.

**`project` materialised view** aggregating from `session` — project_path, session count, latest activity.

**Epoch-level aggregates** maintained as a materialised view from `message` — message count, first/last timestamps per epoch per session.

### JIT Indexing

No eager indexing. On any search/list/extract command:
1. List session files for the relevant project, sorted by mtime descending (newest first)
2. For each file, check `session.modified_at` against actual file mtime
3. If stale or missing, re-index that session file, commit to SQLite immediately
4. Search/query runs against whatever is indexed so far — results are available while older sessions are still being indexed
5. `index` command forces a full scan for explicit rebuilds

**Reverse-chronological indexing:** The most recent sessions are indexed first because they're most likely what the user cares about. A search initiated during indexing returns results from already-indexed (recent) sessions immediately. Older sessions appear in results as they finish indexing.

Current project indexed by default. `--project PATH` to target a specific project.

### CLI Interface

Entry point: `cc-search-chats` (via `[project.scripts]` in pyproject.toml, invokable with `uvx cc-search-chats`).

| Command | Purpose | Key flags |
|---------|---------|-----------|
| `search <query>` | FTS5 keyword search | `--project`, `--epoch`, `--days`, `--json` |
| `extract [session-id]` | Dump conversation text | No args = auto-discover recent substantial session. `--epoch N`. `--json` |
| `list` | List sessions for a project | `--project`, `--days`, `--json` |
| `index` | Force re-index | `--project` |
| `context <uuid>` | Show messages around a specific message | `--depth N`, `--json` |

All commands support `--json` for structured output (subagent consumption).

### Session Discovery Heuristic

For `extract` with no session ID (the crash recovery case):
1. List all JSONL files in the current project's encoded directory
2. Sort by mtime descending
3. Among the top 5 by mtime, rank by file size descending
4. Return the biggest recent file — the most likely "long conversation that crashed"

### Plugin Integration

The Claude Code plugin wraps the CLI:
- `commands/search-chat.md` — slash command that invokes `uvx cc-search-chats <subcommand> --json` via Bash
- `skills/search-chat/SKILL.md` — skill with progressive search workflow (search → broaden → manual exploration)

The skill instructs Claude to use `--json` output and interpret structured results. Sonnet subagents can invoke the same CLI via the Bash tool.

## Existing Patterns

Investigation of the original codebase found:
- Path encoding logic: replace `/` with `-` in project path to find Claude Code's directory. This pattern is correct and matches live data.
- JSONL parsing with line-by-line streaming. The original used embedded Python in a heredoc for this — the approach (streaming, skip malformed) is sound, the packaging was not.
- The original had no indexing — it grepped JSONL files on every search. This design replaces that with SQLite FTS5.

Investigation of akatz-ai/cc-conversation-search found:
- SQLite FTS5 with JIT indexing — validated approach, we adopt this pattern
- Zero dependencies — validated for `uvx` performance, we adopt this constraint
- Session tree structure via `parent_uuid` — we adopt this

This design diverges from akatz-ai in:
- First-class compression awareness (compact_event table, epoch concept) — they don't model this
- Session discovery heuristic for crash recovery — they don't address this use case
- Lazy per-project indexing vs eager all-project indexing

## Additional Considerations

**Error handling:** Malformed JSONL lines are skipped silently (parser returns None). Missing project directories produce a clear error message. SQLite WAL mode for concurrent read safety during Claude Code writes. Partial final lines in actively-written JSONL files are handled gracefully (JSON parse failure → skip).

**Database integrity:** WAL mode can lead to corruption with network filesystems or sync tools (Syncthing, NFS, HPC shared storage). On startup, run `PRAGMA quick_check`. If corruption is detected: print a clear message to stderr explaining what happened ("Index database corrupted, rebuilding from chat history — this may take a moment"), delete the DB, and regenerate from JSONL source files. The index is fully derivable so this is always safe. Similarly, if the DB location (`~/.cc-search-chats/`) appears to be on a network or synced filesystem, warn the user at index creation time.

**Performance on large files:** JSONL files are streamed line-by-line, never loaded into memory. SQLite bulk inserts use transactions (commit every 1000 records). An 8MB file with ~3500 records should index in under 2 seconds.

**Index location:** `~/.cc-search-chats/index.db`. Created automatically on first use. If deleted, regenerated on next command.
